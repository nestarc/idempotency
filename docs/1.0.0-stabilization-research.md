# 1.0.0 안정화 범위와 예상 사용자 불편 조사

조사 기준일: 2026-10-06. 코드 기준: `@nestarc/idempotency` 0.4.0, 커밋 `9610774a767d152c4cbae49c6276a4f2d76463e4`.

실행 문서: [1.0.0 작업판](1.0.0/README.md), [계약과 설계 결정 기록](1.0.0/decisions.md). 이 문서의 S1~S8을 작업별 문서로 분리했다. 이 문서는 조사 근거를 보존하며, 구현 상태와 다음 행동은 작업판과 작업별 인수인계 기록에서 관리한다.

**1.0.0은 기존 기능의 응답 재생 정확성, 격리, 설치 가능성, 장애 시 동작을 확정하는 릴리스로 잡는 것이 적절하다.** 현재 기능 범위는 충분하지만, 기본 테스트가 잡지 못하는 소비자 설치 실패와 Nest 직렬화 조합에서의 정보 노출을 재현했다. 아래 필수 범위를 완료하기 전에는 1.0.0 출시를 권하지 않는다.

이 문서는 조사와 개발 범위 제안이다. 제품 코드나 기존 테스트는 수정하지 않았다. 외부 사례는 해당 프로젝트 사용자의 보고이며, 이 패키지의 이용률이나 장애 발생률을 뜻하지 않는다.

이 패키지 자체의 [공개 이슈](https://github.com/nestarc/idempotency/issues)는 조사 시 GitHub API에서 반환된 24개 항목이 모두 Dependabot PR였고 일반 이슈는 없었다. 공개 검색만으로 실제 도입자의 불편을 직접 확인하기는 어렵다. 위 표는 인접 생태계의 문제 신호이며, 수요 규모를 측정한 결과는 아니다.

공식 운영 정책도 범위를 제한한다. [Stripe webhook 문서](https://docs.stripe.com/webhooks#event-delivery-behaviors)는 live 자동 재전송 최대 3일, Dashboard 수동 재전송 15일, CLI 30일을 설명한다. 기본 24시간 TTL만으로 webhook 중복 전체를 막는다고 설명해서는 안 된다. event ID 중복과 서로 다른 이벤트가 같은 업무 변경을 유발하는 경우도 구분해야 한다.

[Stripe idempotency 문서](https://docs.stripe.com/api/idempotent_requests)는 첫 결과의 실패·500도 재생한다고 설명한다. 현재 패키지는 handler exception에서 레코드를 삭제하므로 Stripe와 같은 오류 정책을 제공한다고 볼 수 없다. [AWS의 재시도 설계 설명](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)도 idempotency 기록과 업무 변경을 함께 다루는 원자성의 중요성을 보여준다.

## 재현한 출시 차단 문제

### 응답 직렬화 이후의 값이 보존되지 않는다

Fastify와 Nest `ClassSerializerInterceptor`, class-transformer 0.5.1 조합에서 직렬화 인터셉터가 바깥쪽, idempotency 인터셉터가 안쪽일 때 다음 결과를 재현했다. 전역 serializer와 컨트롤러·메서드 idempotency의 조합에서도 고려해야 하는 순서다.

```text
컨트롤러 반환: User 인스턴스 { id: 1, secret: 'example-secret' }
secret에는 @Exclude() 적용
첫 HTTP 응답: { id: 1 }
같은 키의 재요청: { id: 1, secret: 'example-secret' }
handler 실행 횟수: 1
```

인터셉터가 원래 클래스 객체를 [JSON.stringify로 저장](https://github.com/nestarc/idempotency/blob/9610774a767d152c4cbae49c6276a4f2d76463e4/src/idempotency.interceptor.ts#L406)한 뒤, [JSON.parse로 복원](https://github.com/nestarc/idempotency/blob/9610774a767d152c4cbae49c6276a4f2d76463e4/src/idempotency.interceptor.ts#L268)하면 클래스의 직렬화 메타데이터가 사라진다. 그 결과 최초 응답에서는 제외된 속성이 replay에 포함된다. Nest의 [직렬화 문서](https://docs.nestjs.com/application/serialization)에서도 클래스 인스턴스와 일반 객체의 차이가 중요하다.

같은 영역의 추가 재현 결과는 다음과 같다.

- `StreamableFile(Buffer.from('hello'))`: 최초 응답은 바이너리 `hello`, replay는 options/logger/stream 내부 구조를 포함한 JSON으로 바뀐다. [isReplayable](https://github.com/nestarc/idempotency/blob/9610774a767d152c4cbae49c6276a4f2d76463e4/src/idempotency.interceptor.ts#L713)이 Nest 래퍼를 판별하지 못한다.
- 수동 `@Res().send()` 경로: 첫 응답은 성공하지만 replay에서는 handler가 호출되지 않아 응답 완료 경로가 사라졌다. Fastify 주입 실험에서 250ms 관찰 제한 안에 완료되지 않았다.
- 여러 값을 내보내는 Observable: [각 emission마다 complete 호출](https://github.com/nestarc/idempotency/blob/9610774a767d152c4cbae49c6276a4f2d76463e4/src/idempotency.interceptor.ts#L337)로 인해 원 요청이 끝나기 전에 중간값이 COMPLETED로 저장되고 다른 요청에 재생됐다.

1.0에서는 일반 JSON/Promise 응답의 안전한 serializer 순서를 검증하고, 지원하지 않는 응답 경로에는 명시적인 제한과 테스트가 필요하다. 파일·스트리밍 전체 지원은 필수가 아니지만 잘못된 응답을 재생하는 상태로 두어서는 안 된다.

### 선택 의존성 없이 설치할 수 있다는 계약이 깨진다

[PostgresStorage의 pg 값 import](https://github.com/nestarc/idempotency/blob/9610774a767d152c4cbae49c6276a4f2d76463e4/src/storage/postgres.storage.ts#L3)가 [루트 재수출](https://github.com/nestarc/idempotency/blob/9610774a767d152c4cbae49c6276a4f2d76463e4/src/index.ts#L9)을 통해 실행된다. pg가 없는 독립 소비자에서 MemoryStorage만 import해도 `Cannot find module 'pg'`가 발생했다.

복사한 dist와 package.json으로 구성한 소비자에서 `strict: true`, `skipLibCheck: false`로 확인한 타입 문제도 있다. 선택 peer가 없으면 pg와 ioredis의 TS2307이 발생하고, 둘을 설치해도 `@types/pg`가 없으면 TS7016이 발생한다. 런타임 lazy import만 수정해서는 충분하지 않다.

### 사용자 범위와 키 조합이 쉽게 충돌한다

[README tenant 예제](https://github.com/nestarc/idempotency/blob/9610774a767d152c4cbae49c6276a4f2d76463e4/README.md#L269)는 tenant ID만 반환한다. custom scope가 [기본 endpoint scope를 대체](https://github.com/nestarc/idempotency/blob/9610774a767d152c4cbae49c6276a4f2d76463e4/src/idempotency.interceptor.ts#L589)하므로 같은 tenant의 `/payments`와 `/refunds`에 같은 키·body를 보내면 refund handler는 실행되지 않고 payment 응답이 재생됐다. 사용자 정의 scope가 그렇게 동작하는 것은 현재 API 계약이지만, 문서가 안전한 사용을 유도하지 못한다.

단순 `::` 연결도 구성요소의 경계를 보장하지 않는다. `POST /payments`와 키 `archive::K`가 `POST /payments::archive`와 키 `K`의 저장 키와 일치하는 것을 재현했다. 구성요소를 모호하지 않게 인코딩하고, tenant/user와 endpoint를 함께 사용하는 방법을 확정해야 한다. 현재 기본 endpoint scope 자체에는 사용자 식별자가 포함되지 않는다.

### 관측 이벤트의 원본 키 비노출 계약이 지켜지지 않는다

[emitEvent](https://github.com/nestarc/idempotency/blob/9610774a767d152c4cbae49c6276a4f2d76463e4/src/idempotency.interceptor.ts#L667)는 keyHash 외에 `scope: scopedKey`도 보낸다. 이벤트의 scope가 `POST /p::sensitive-business-key`임을 재현했다. [0.4 명세의 원본 키 비노출 요구](https://github.com/nestarc/idempotency/blob/9610774a767d152c4cbae49c6276a4f2d76463e4/docs/superpowers/specs/2026-06-16-v0-4-0-scope-spec.md#L345)와 다르며, 일부 오류 로그에도 전체 scopedKey가 들어간다.

## 장애와 저장소 계약에서 확정할 사항

| 현재 동작과 근거 | 판단 |
| --- | --- |
| `complete()`의 비동기 rejection은 잡지만, Promise 반환형의 custom adapter 메서드가 동기적으로 throw하면 성공한 handler의 결과가 오류로 바뀌고 레코드가 삭제된다. [호출 지점](https://github.com/nestarc/idempotency/blob/9610774a767d152c4cbae49c6276a4f2d76463e4/src/idempotency.interceptor.ts#L429). 별도 probe로 재현했다. | 저장 후처리의 동기 throw와 rejection을 동일하게 격리해야 한다. 사용자 정의 어댑터도 공식 확장 계약이다. |
| 바깥쪽 RxJS timeout으로 구독이 종료된 뒤 async 업무 처리는 끝났지만 PROCESSING이 남았다. | 취소가 업무 취소를 뜻하지 않는다. 안전하지 않은 자동 delete 대신 결과 불명 상태, lease 만료, 조정 절차를 문서화하고 검증한다. |
| [handler exception은 레코드를 삭제](https://github.com/nestarc/idempotency/blob/9610774a767d152c4cbae49c6276a4f2d76463e4/src/idempotency.interceptor.ts#L341)한다. | 외부 결제나 DB 변경 후 예외가 난 경우 재시도가 업무를 다시 실행할 수 있다. 전체 exactly-once 보장은 현재 구조의 범위 밖이다. |
| MemoryStorage에 30일 TTL을 주면 [타이머 정수 범위 초과](https://github.com/nestarc/idempotency/blob/9610774a767d152c4cbae49c6276a4f2d76463e4/src/storage/memory.storage.ts#L138) 경고 후 20ms 관찰 시점에 키가 사라졌다. | 개발용 어댑터라도 동일 설정의 의미를 보존하거나 상한을 명확히 검증해야 한다. |
| Memory에서 만료 타이머 실행 전 시계를 lease 이후로 이동하면 create는 거절되고, 옛 token의 complete는 성공해 레코드가 다시 유효해졌다. | create/complete의 만료 판정도 공통 계약에 포함한다. |
| [Postgres complete SQL](https://github.com/nestarc/idempotency/blob/9610774a767d152c4cbae49c6276a4f2d76463e4/src/storage/postgres.storage.ts#L189)은 PROCESSING을 요구하지만 expires_at은 검사하지 않는다. Memory/Redis는 같은 token으로 반복 complete가 가능하다. | 반복 complete와 만료 후 complete의 동작을 통일한다. PG 부분은 SQL 확인이며 실제 DB 재현은 미실시다. |

저장소 CAS는 오래된 요청이 새 token의 레코드를 덮어쓰지 못하게 한다. 이것만으로 오래된 요청의 업무 실행을 중단하거나, 업무 DB commit과 응답 기록 사이의 장애를 제거하지는 못한다. 짧은 processingTtl이나 heartbeat를 추가해도 이 경계는 남는다.

## 1.0.0 필수 개발 범위와 완료 기준

| 작업 | 개발 범위 | 완료 기준 |
| --- | --- | --- |
| S1 응답 재생 정확성 | 직렬화 순서 확정, 지원 응답 범위, Observable 완료 시점, 수동 응답 처리 | Express/Fastify에서 최초 응답과 replay의 status/body/허용 헤더가 일치. Exclude/Transform 속성이 새지 않음. 중간 emission을 완료로 저장하지 않음. 미지원 파일·수동 응답이 잘못 재생되거나 대기 상태로 남지 않음. |

S1·S2·S3·S4의 재현 결함을 먼저 고치고, S5·S6의 상태 전이 계약을 확정한다. S7·S8로 소비자가 그대로 설치하고 운영할 수 있는지 확인한 뒤 RC를 거쳐 1.0.0을 내는 순서가 적절하다. 버전 중간 번호나 일정을 미리 확정하기보다는 이 완료 기준으로 출시를 판단한다.

S7에서 바로 수정할 문서·연결 문제는 다음과 같다.

- [Postgres sweep 예제](https://github.com/nestarc/idempotency/blob/9610774a767d152c4cbae49c6276a4f2d76463e4/README.md#L221)는 PostgresStorage 클래스 provider를 등록하지 않지만 서비스가 그 토큰을 요구한다. 예제를 그대로 구성한 Nest TestModule에서 DI 실패를 재현했다.
- [관측 예제](https://github.com/nestarc/idempotency/blob/9610774a767d152c4cbae49c6276a4f2d76463e4/README.md#L343)의 `new PostgresStorage(pool)`은 생성자 계약 `{ pool }`과 다르다.
- README의 “키당 at most once”, Redis의 무조건적인 durability 표현은 lease·장애·서버 persistence 설정 조건을 반영해야 한다. invalid TTL은 일반 Error인데 오류 표는 400으로 설명한다. roadmap도 0.4를 진행 중으로 표시한다.
- 기본 scope를 custom scope로 교체할 때 tenant만 붙이면 endpoint 격리가 사라진다는 사실을 명시한다. 키 구성이나 fingerprint 형식 변경으로 배포 전후 요청이 별도 작업으로 인식되지 않도록 호환 읽기 또는 레코드 보존기간을 고려한 전환 전략이 필요하다.

2026-10-06 기준 [Node 공식 릴리스 표](https://nodejs.org/en/about/previous-releases)는 22/24를 LTS, 20을 EOL로 표시한다. 현재 CI는 20/22이므로 22/24를 필수 대상으로 삼고 20 유지 여부를 명시적으로 결정하는 편이 적절하다. [CI의 Redis smoke](https://github.com/nestarc/idempotency/blob/9610774a767d152c4cbae49c6276a4f2d76463e4/.github/workflows/ci.yml#L137)는 이미 있지만 [release 검사 잡](https://github.com/nestarc/idempotency/blob/9610774a767d152c4cbae49c6276a4f2d76463e4/.github/workflows/release.yml#L87)에는 Redis 환경이 없어 해당 검사가 skip될 수 있다.

[IETF datatracker](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/)는 draft-07을 2026-04-18 만료·보관 상태로 표시한다. RFC 준수를 약속하지 말고 구현한 프로파일을 명시해야 한다. [draft의 Structured Field 문자열 규칙](https://datatracker.ietf.org/doc/html/draft-ietf-httpapi-idempotency-key-header-07#section-2.1)과 현재 raw header 처리의 차이, 반복 헤더·빈 값·최대 길이·custom resolver 반환값의 정책을 1.0 전에 고정한다. 규격 확장 전체를 구현할 필요는 없다.

## 1.0 이후로 미룰 범위

다음 기능은 이번 공개 사용자 증거와 코드 상태만으로 1.0 필수라고 볼 근거가 약하다.

- `@TransactionalIdempotent`와 ORM별 transaction 통합. 업무 원자성은 중요하지만 범용 API 설계 범위가 크다. 1.0에는 보장 경계와 DB unique constraint/inbox/outbox 예제를 제공한다.
- 자동 lease 연장, 중복 요청 wait 모드, 범용 retry 엔진, 관리용 강제 unlock API. 장애·취소·중복 실행 정책을 먼저 확정해야 한다.
- business-error caching의 광범위한 옵션. 현재 기본 정책과 실패 후 재실행 조건은 필수로 문서화하되, 어떤 오류를 보존할지에 대한 사용자 요구를 확인한 뒤 추가한다.
- 새 저장소 어댑터, 큐·RPC·GraphQL 전체 지원, dual ESM/CJS, Swagger 자동화. 기존 HTTP/Nest 도입 경로 안정화보다 우선하지 않는다. 현재 CJS의 소비자 호환성 검증은 S2에 포함한다.
- 대규모 benchmark·성능 최적화. 목표 payload 크기·RPS·지연 예산이 확인된 뒤 설계한다. 정확성이나 저장소 장애를 성능 수치로 대체하지 않는다.

RC 검증 대상으로 단일 사용자 JSON API, multi-tenant API, Postgres 기반 webhook 수신기의 세 구성을 권한다. 확인할 내용은 처리시간·최대 응답 크기, 실제 serializer/인증 배치, 재전송 기간, 같은 작업을 식별하는 방식, 장애 때의 수동 복구 절차다. 실제 도입팀 피드백 없이 이 조사만으로 시장 검증이 끝났다고 판단하지 않는다.

## 실행한 검증과 남은 한계

- Node 24.11.1, npm 11.6.2 환경에서 lint, 타입 검사, build, npm pack dry-run 성공.
- `npm run test:all -- --runInBand`: 15 suite 통과, 6 suite skip. 테스트 198개 통과, 39개 skip.
- 처음에는 샌드박스의 로컬 포트 제한으로 HTTP E2E가 실패했으나, 로컬 테스트 서버 실행을 허용한 재실행에서는 통과했다. 이 실패를 제품 결함으로 계산하지 않았다.
- skip된 검사는 Postgres 관련 28개와 실제 Redis 11개다. Docker daemon이 없었으며 실제 DB 테스트 성공을 주장하지 않는다.
- 추가 재현은 독립 소비자 fixture, Nest TestModule, 인터셉터·저장소 probe, Fastify in-process HTTP 실험으로 수행했다. ClassSerializer 실험은 이미 로컬에 있던 class-transformer 0.5.1을 사용했다. 기존 198개 테스트에 이 probe 수를 합산하지 않았다.
- 실제 PG에서의 만료·반복 complete 검증, 다중 프로세스 장애 주입, 실제 npm tarball 소비자 matrix, 호환 버전 matrix 전체 실행은 S6·S8의 남은 완료 조건이다. pack dry-run 성공은 설치·런타임 안전성의 증거가 아니다.
